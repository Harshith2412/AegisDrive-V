# Cybersecurity item and secure communication design

The item remains simulated longitudinal AEB with radar/camera fusion, three native C++
ECUs, backup command transport and achieved-deceleration supervision. New Python SiL
security gateways validate ingress before native ECU input. No claim of embedded SecOC,
AUTOSAR conformance, HSM integration, ISO/SAE 21434 compliance or automotive certification
is made. [AUTOSAR's public SecOC specification](https://www.autosar.org/fileadmin/standards/R24-11/CP/AUTOSAR_CP_SWS_SecureOnboardCommunication.pdf)
is conceptual inspiration only. Algorithms are unchanged; authentication cannot establish
correct perception, safe intent, available grip or working physical actuation.

## Concrete protected PDU

Every protected PDU is **exactly 64 bytes**, a valid CAN FD payload length, with no implicit
Classical CAN overloading or undefined fragmentation. Classical 8-byte ECU payloads remain
inside this envelope and retain their CRC/alive counter. After authentication, the local
trusted adapter supplies the original eight bytes to native C++; it is not transmitting a
64-byte protected PDU over Classical CAN. The virtual capacity model is frame-budget based,
not CAN/CAN-FD bit-level timing. Mode A transports the original eight-byte payloads.

| Offset | Field | Width / interpretation |
|---|---|---|
| 0 | version | 8 bits, fixed 1 |
| 1/2/3 | sender / destination / key ID | 8 bits each; static authorization table |
| 4 | message identifier | 16-bit big-endian; only 11-bit IDs permitted |
| 6 | boot epoch | unsigned 32-bit big-endian, initially pinned 1 |
| 10 | freshness counter | unsigned 64-bit big-endian, per sender/destination/message/key/channel |
| 18 | authenticated send time | unsigned 64-bit simulation milliseconds |
| 26 | payload length | 8 bits, 0–21 at envelope layer |
| 27–47 | payload, then zero padding | command/status exactly 8 bytes at application gateway; sensor exactly 21 |
| 48–63 | authentication tag | first 16 bytes of HMAC-SHA256 |

MAC input = fixed `AegisDrive-V/v0.4/` channel domain + terminator + first 48 PDU bytes.
Thus all identities, key ID, message ID, epoch, full counter, time, length, payload and
padding are protected. Channel domains and backup command key separation prevent moving a
primary PDU onto the backup path. Verification uses Python's established `hmac.digest`
SHA-256 implementation and `compare_digest`, not project-written cryptography; the standard
[RFC 4231 vector](https://www.rfc-editor.org/rfc/rfc4231) is tested. No encryption or privacy
protection is offered. A 128-bit tag is an educational parameter, not a measured forgery
probability or a complete key-management security argument.

## Identities and covered paths

ADAS=1, Brake=2, Body=3, Radar=4, Camera=5; test unauthorized node=9. IDs: 0x120 command
ADAS→Brake; 0x130 ADAS status→Body; 0x220 Brake status→ADAS/Body (destination 0 authorized
broadcast to these receivers only); 0x300 radar→ADAS/fusion; 0x301 camera→ADAS/fusion.
Each native status subscriber has its own verifier/replay state. Gateway cache prevents a
second sample of the same broadcast by the same subscriber from becoming a spurious replay.
Sender logging strings are never authorization evidence; attack provenance labels affect
only experiment counters. Trusted local ego-speed, ideal IMU/plant, FFI and actuator outputs
remain outside message authentication. Runtime diagnostics are local, not authenticated
remote telemetry. No network service or real vehicle is contacted.

The sensor PDU packs float32 range/rate/confidence, uint64 acquisition timestamp and one flag
byte. Authentication send time does not replace acquisition time: frozen data still ages
out. Sensor signing occurs after the existing sensor delivery queue; no extra physical
sensor bus/arbitration is introduced. Float32 wire quantization differs from Mode A's
float64 direct objects; matched inputs can therefore yield small separation/timing changes.
Both effects and limitations are disclosed in evaluation. Authentication/FFI CPU overhead is
measured separately; zero modeled cryptographic scheduling time is not a real-time guarantee.

## Test keys, provisioning and trust

`TEST_KEYS` contains eight distinct **public, predictable, 32-byte test fixtures**. They are
not secrets, never production keys and not a custom key derivation scheme. Keys 1–5 separate
command/status/radar/camera purposes, key 6 is backup command, key 7 is an unauthorized-node
fixture; reserved key 8 is unused. Channel domain binding supplements separation. Every
verifier has a static sender/destination/message/key policy. Symmetric broadcast recipients
and shared services holding a key can impersonate its producer; no nonrepudiation is claimed.
The threat model restricts outsiders to unsigned/captured packets unless producer/key
compromise is explicitly injected. Knowing public fixtures in this test environment is
not evidence of protected real-world key provisioning or resistance to key extraction.

Provisioning pins epoch 1 and the role/key table out of band. Retained receiver freshness
state is an in-memory **NVM abstraction** surviving verifier reconstruction when the same
store is supplied. It is not durable/tamper-resistant storage; simultaneous rollback of
all retained state is an open vulnerability. No secure boot, key rotation/revocation,
service authorization or trusted clock implementation is provided.

## Freshness, restart and recovery policies

B accepts an authenticated packet only at age 0–100 ms, matching pinned epoch, strictly
increasing full counter with jump <=32. Duplicates/out-of-order packets are rejected, not
buffered. MAC or freshness failure never advances retained state. Negative/future time,
malformed length/version/padding/route and incorrect authorization fail closed. Application
payload length and native CRC/plausibility still apply after successful MAC verification.

C preserves MAC/age/monotonicity checks but permits authenticated forward jumps <=4096 and
exactly +1 boot epoch, logging RESYNC. This can restore availability after modeled loss or
an authorized freshness-manager fault; it is not permission to learn arbitrary epoch or
accept rollback. Counter exhaustion at 2^64 raises an error instead of wrapping. Sender
restart advances retained boot epoch and resets counters; epoch 2^32−1 exhaustion also
fails closed pending explicit reprovisioning. B deliberately needs out-of-band epoch
reprovisioning; C can accept the next authenticated epoch. Timestamp/counter state loss,
clock manipulation or legitimate-key compromise are not solved by a tag.

A10 first rolls the sender counter back in the same epoch (rejected); C then performs a
modeled retained-epoch restart after 200 ms. This is an explicit authorized recovery action,
not automatic acceptance of a replay. A06 counter jumps and A11 signed implausible values
require authorized producer/state privilege or a fault: outsiders cannot invent valid tags.
A12 and shared-key compromise deliberately demonstrate dangerous correctly signed commands.

## Safety/security supervision

The C++ ADAS supervisor latches a security-event DTC through ABI 4. It does not start blind
braking or equate every rejected packet with unavailable actuation. Native input/feedback
watchdogs retain their existing behavior, so losing all legitimate commands can cause
collision even when every forged message is rejected. Healthy backup may preserve demand;
shared gateway/key/ECU/actuator failures remain common dependencies. A gateway-down injection
is not mislabeled an observed detection timestamp: ordinary feedback timeout is measured.

Queues are capped at 64 frames, service at four frames/step, flood injection at six/step.
Diagnostic recent-event buffers cap at 128; aggregate counts/timing accumulators are bounded
in shape. Backlog observation, not attack ID, triggers bus-pressure diagnostic events.
Security events and resource limits are useful observability, not proof of safe availability.

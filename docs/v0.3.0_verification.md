# Verification scope, budgets and limitations

Baseline reproduction: 39 C++ + 23 pytest tests passed before changes. New tests cover
within-step contact, split stop dynamics, friction stopping-distance identities, warning
ODD exit, camera timing/FOV/probability, fusion health/gates/alignment, backup validation and
arbitration, independent achieved-deceleration supervision, fault containment and regression.
Hypothesis runs 100 generated cases each for tire-limited motion and causal fusion alignment,
with deterministic generation and no database. These generated examples supplement explicit
boundaries; they are not counted as 200 separately linked requirement tests. Fixed grids
exercise additional friction/speed/age/rate combinations. All existing tests are retained;
the reproducibility test now excludes newly introduced process-CPU timings just as it already
excluded wall-clock timings. Its physical/data reproducibility comparison remains strict.

Five new requirements are project-specific derived assurance allocations. The database has
44 requirements. The checker label VERIFIED means listed executed tests pass; it does not
mean every natural-language operating condition or safety goal has been exhaustively proven.
The prior requirement acceptance scopes remain visible. Positive failover tests coexist with
negative tests asserting retained collisions/ghost braking where the design cannot prevent
them. Passing a characterization case is not a claim that its hazardous behavior is acceptable.

## Time budgets

- Control step 10 ms, radar 50 ms, camera 50 ms with default 80 ms delivery latency.
- Per-source maximum sample age 150 ms. A 50 ms sampling period plus 120 ms latency can
  cause intermittent age rejection; this is measured in adverse/hold-out cases, not hidden.
- Primary transport at least one step; backup configured 20 ms. Delay/duplicate cases are
  causal queues, not a claim of real CAN worst-case arbitration or processor scheduling.
- Brake buildup time constant 150 ms. Command-to-reported-active and command-to-physically
  achieved braking differ under actuator failure; current evaluation uses the latter.
- Feedback/accepted-progress watchdog >100 ms. Received last-valid time, rather than send
  time, determines its next-step detection; feedback loss at 2 s is indicated at 2.11 s.
- Achieved response buildup allowance >300 ms, then persistent mismatch >=200 ms; diagnostics
  may precede or follow hazard progression. No vehicle FTTI or driver-rescue guarantee exists.
- CPU measurements use `process_time_ns` around the ctypes call; process CPU, FFI, timer and
  concurrency overhead are included. They are not target ECU-only execution time or WCET.

Physical contact is now resolved within the integration step. Nonintegral step horizons are
rejected rather than silently rounded; a short braking trace checks final state at the horizon. Unavailability duration stops
at contact/horizon, rather than counting a full last interval after contact. Single-source
mode-transition metrics exclude the first 150 ms startup grace to avoid counting normal
camera initialization as successful fault recovery. Missed detection counts unusable/stale
sources as well as nondetections, per control cycle; cached measurements make these counts
correlated. The raw source confidence and health model remain assumptions.

## MC/DC engineering

Baseline: 180 instrumented conditions, 45.00% covered, six ECU source files, C++ unit +
Python integration scope. The new report uses the same file scope and test categories but
modified source, so denominators differ; percentages alone are not a controlled coverage
comparison. `mcdc_conditions.json/.md` enumerate every reported decision location, ordered
condition flags, source snippet and uncovered conditions. LLVM's report is authoritative;
trivial decisions and uninstrumented/excluded constructs are not inferred covered.

Meaningful independent-condition cases added include invalid configuration values one at
a time (finite/positive/range/order/timer contracts), achieved-input validity, NaN, lower/upper
range and future/stale timestamps from an otherwise valid tuple; adequate vs grossly missing
achieved deceleration; and backup CRC/DLC/range/repeated-counter rejection without refreshing
accepted demand. These test safety contracts rather than restructuring expressions to improve
coverage. The monitor-enablement independence regression also caught and corrected coupling
between the optional IMU monitor and disabled feedback monitor.

Coverage still misses conditions, notably C API null/error paths and some codec/feedback/
config combinations; exact current gaps and counts are retained, not rounded to full coverage.
No MC/DC adequacy, qualified-tool or standards-compliance claim is made. Final coverage logs
are checked for stale/mismatched profile warnings; profiles are reset before each run.

## Failed attempts and evidence corrections

Increment logs retain an incorrectly chosen positive-gap contact fixture, a new CPU timing
field initially included in a deterministic equality test, and a one-cycle error in a feedback
loss test expectation. The fixtures/expectations were corrected from the equations and delivery
ordering; functionality was not weakened to hide failures. First experiment attempts are
retained. Metric corrections classify stale radar as a missed usable detection, distinguish
software brake-active from achieved braking, exclude startup degraded-mode inflation, and
truncate duration at contact. A camera confidence bug initially restored nominal confidence
on nondetection in poor visibility; the final model consistently applies scene quality even
to nondetections. No braking/fusion threshold was tuned against held-out outcomes. The case
manifest is unchanged across these reruns and checked by SHA-256.

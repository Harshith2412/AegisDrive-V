# Toolchain and reproducibility record

Executed on macOS arm64 (Darwin 25.5.0), AppleClang 17.0.0 (clang-1700.0.13.5),
CMake 4.2.3, Python 3.14 in `.venv`. Compiler/CMake/LLVM version outputs and the complete
Python dependency freeze are in `results/v0.2.0/`. `environment.json` adds OS/architecture,
clock convention and executable versions. All ECU core/C ABI targets compile with
-Wall -Wextra -Wpedantic -Wconversion -Wshadow -Werror. Current final build emits no diagnostics.
Unit-test sources use their existing -Wall -Wextra options.

CMake + the bundled minitest compatibility runner and real pytest were executed. GoogleTest
FetchContent was not executed; no GoogleTest equivalence or independent framework qualification
is claimed. python-can is optional and not installed/tested. The default deterministic bus is
used for all scenarios. Model validation used Java 21.0.10 and PlantUML 1.2026.2; the jar was
obtained from Maven Central, kept outside the source tree, and its hash is recorded. The
bundled Smetana layout avoids requiring Graphviz. Java needed execution outside the sandbox.

A local venv install initially failed under restricted network access, then succeeded with
network access for declared dependencies. The new environment uses the exact versions recorded
in `dependencies.txt`; the original archived evidence used Linux/Python 3.12 and GCC 13.
The unchanged baseline was rebuilt/rerun in the same new macOS environment as the candidate.
Comparisons use identical YAML files and seeds 0–19; extra cases use identical parameters via
`tools/evaluate_assurance.py`. Do not compare host microsecond timing as ECU execution time.
No project Git history existed; no commit hash/tag can identify this baseline. Archive and
source hashes identify the compared sources instead. Baseline archive checksum is recorded
in `baseline/v0.1.0/SHA256SUMS`. Do not recreate that archive from modified sources.

## Reproduce candidate

```sh
python3 -m venv .venv
.venv/bin/pip install -r results/v0.2.0/dependencies.txt
AEGIS_MCDC=ON PLANTUML_JAR=/path/to/plantuml-1.2026.2.jar scripts/run_all.sh
```

`run_all.sh` preserves original `results/` evidence and writes v0.2.0 outputs in its own directory.
Linux uses the same CMake and tests; the LLVM reporting script currently targets macOS dylib
and xcrun paths. GCC coverage remains available via the original script but writes the original
results path, so archive/copy that evidence before running it. No Linux v0.2.0 build is claimed.
On a Clang lacking MC/DC use AEGIS_MCDC=OFF and report MC/DC as unavailable, never infer it
from branch coverage. No stale profiles are merged: the LLVM script deletes its old profraw
files before running the unit and Python suites. Coverage excludes the scenario evaluation run.

## Reproduce unchanged baseline

Extract `baseline/v0.1.0/source-and-evidence.tar.gz` into a separate directory, configure its
CMake build with `-DAEGIS_USE_MINITEST=ON`, and run its original tests/experiment runner with the
same venv packages. For the paired extra cases, run the current evaluator with
AEGIS_SOURCE_ROOT pointing to that extracted directory and AEGIS_ECU_LIB pointing to its
baseline library. The evaluator imports baseline modules through this override. The baseline
was executed before any candidate source edits in this session. Archived v0.1.0 source has ABI 1;
the candidate has ABI 2, and must never load the baseline library with candidate bindings.

## LLVM coverage and MC/DC investigation

The installed compiler accepted -fprofile-instr-generate -fcoverage-mapping -fcoverage-mcdc,
and installed llvm-cov reported MC/DC on actual ECU expressions. An initial CMake flag check
failed at linking because the probe omitted the profiling runtime link option; the check was
corrected to link with -fprofile-instr-generate. This was a probe error, not lack of compiler
support. The executed probe/configuration and full coverage-build logs are preserved.

Workflow follows [Clang source-based coverage documentation](https://clang.llvm.org/docs/SourceBasedCodeCoverage.html).
Actual output is authoritative for this Apple build. Flags/options described by newer upstream
LLVM are not assumed to work without testing. Summary is 98.22% lines, 94.94% regions, 80.30%
branches, and 45.00% instrumented MC/DC conditions over six ecu/src files. MC/DC has substantial
uncovered conditions and excludes trivial single-condition decisions by tool definition.
This is partial structural evidence, not 100% MC/DC, tool qualification or a safety adequacy
finding. Header inline code, Python logic, simulator plant, and uninstrumented libraries are
not included in the six-file denominator. Original GCC/gcov numbers use a different scope
and cannot be treated as a before/after coverage improvement.

The first combined unit/shared-library coverage report warned of one profile mismatch.
The llvm-cov debug dump isolated it to inline AdasEcu::state() (header code) because test
translation units were not instrumented consistently with the library. The CMake coverage
configuration now instruments test translation units with the same coverage/MC/DC flags.
Profiles were discarded and the coverage suites rerun. The investigation dump is retained
in coverage-mismatch-investigation.txt; final coverage-build.log records the corrected run.

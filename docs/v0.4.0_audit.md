# Architecture and security-gap audit — before implementation

The v0.3.0 repository is preserved in baseline/v0.3.0/source-and-evidence.tar.gz,
with its SHA-256 checksum. Reproduction writes exclusively results/v0.4.0/baseline.
Existing result files and all prior hashed archives must remain unchanged.

## Interfaces and trust boundaries

| Path | Existing validation | Authentication in v0.3.0 |
|---|---|---|
| Radar/camera to fusion | Health, confidence, finite/plausible values, acquisition age; sensor models share scene | NONE; Python direct-object input |
| Fused target/ego speed to ADAS | C ABI version/size and ADAS validity/freshness/range gates | NONE; trusted local FFI boundary |
| ADAS -> Brake primary CAN 0x120 | CRC-8, modulo-16 alive counter, payload range/reserved-bit validation | NONE |
| ADAS -> Brake backup | Independent E2E receiver; primary priority; same ECU and actuator | NONE |
| Brake -> ADAS/Body 0x220 | CRC/counter/payload checks independently per subscriber | NONE |
| ADAS -> Body 0x130 | CRC/counter/payload checks | NONE |
| Achieved-deceleration input -> supervisor | Validity, timestamp and range checks; ideal previous plant sample | NONE; local trusted plant/IMU abstraction |
| C++ actuator -> plant / lamps | Local modeled outputs | NONE; no remote interface modeled |
| Diagnostics/security state | Local DTCs, no security gateway/keys previously | NONE |

No existing communication path is cryptographically authenticated. CRC/counters detect
accidental corruption and limited repetition; a local on-bus adversary can recompute CRC
and choose the next modulo counter. CRC does not identify an authorized sender. Sender
strings in CanFrame are logging metadata, not trustworthy identities. Trusted local FFI,
plant and clock are explicit simulation boundaries, not production protection mechanisms.

Assets: justified brake demand/actuation, radar/camera target evidence, state/lamps,
communication availability, supervisor/diagnostic integrity, future keys and freshness state.
Trust boundaries: untrusted transport -> ECU ingress verifier; sensor producer -> fusion;
primary vs backup transport; shared security service; local operator provisioning vs runtime.
The proposed security gateway is a new modeled verification boundary, not an existing ECU.

## Hold-out failures and attribution discipline

The locked original 120 configurations and outcomes are retained. Twenty-nine collisions
are analyzed from actual inputs and replayed counterfactual ideal-sensor/zero-network-delay
cases in holdout_root_causes.json/.md. Classification distinguishes speed-window exclusion,
insufficient initial physical stopping distance, low-grip planning assumptions and remaining
controller/perception/timing interactions. Categories are hierarchical primary groups plus
nonexclusive contributing factors, not proof of a unique root cause. None of these inputs
contains a cyberattack; they remain functional/ODD/SOTIF limitations.

## Smallest defensible secure increment

Retain the existing ECU algorithms/E2E payloads. Place an educational CAN FD authentication
boundary around ADAS -> Brake before expanding to status and sensor ingress. Use Python's
standard hmac/hashlib HMAC-SHA256 implementation, explicit 128-bit tags, bounded framing,
sender policy and full 64-bit freshness state. Gate untrusted data before passing original
8-byte payloads into C++ so no successful cryptographic check bypasses ECU plausibility.
This is SiL gateway authentication, not embedded AUTOSAR SecOC or HSM implementation.
No universal emergency action follows rejection: reduced availability can itself cause a
collision and must be measured, including shared gateway/key failures and compromised
legitimate senders. Cryptographic identity cannot establish correct target/command intent.

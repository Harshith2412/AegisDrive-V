# Actuation, diagnostics and fault containment

The two command paths are separate scheduled simulation queues carrying the same E2E
protected demand to **one Brake ECU and one actuator**. Primary and backup have separate
counter-validation state; both synchronize continuously. Valid primary demand takes
precedence when both are valid. Backup delivery is 20 ms by default; primary one step
unless delayed. They do not model separate power, wiring routing, processors or hydraulics.
No physical independence or quantitative diagnostic coverage is established.

| Fault | Containment/detection | Recovery actually modeled | Residual risk |
|---|---|---|---|
| A primary request lost | Accepted-counter progress/Brake timeout; independent backup receiver | Healthy backup continues same actuator command | Both paths lost still release after 100 ms and can collide |
| B feedback lost | Status/ack watchdog >100 ms (next step), indicated unavailable | Command delivery continues; no blind command added | Brake assurance absent despite possible healthy braking |
| C Brake ECU software failure | Modeled fail-silent process stops status and actuator output; status watchdog + achieved-decel diagnostic | No independent Brake ECU | Collision remains despite both queues; other software failures not represented |
| D actuator unable to brake | Delivered brake decel forced zero while software/ack remain alive; achieved-decel mismatch diagnostic | No alternate physical actuator | Collision remains; retries/acks cannot supply braking |
| E intermittent requests | Counter gaps/rejections/timeout; healthy backup | Next valid frames resynchronize under existing E2E policy | Common intermittent faults can exceed timing margin |
| F delayed/duplicated requests | Scheduled transport, independent counter checks; receiver prefers latest generated deliverable frame | Backup may deliver earlier valid requests | Old-but-sequential primary is not timestamp-protected; no general stale-demand guarantee |
| Common channel loss | Both queues drop | None | Single actuator command unavailable |
| Low tire grip | Plant min(request,mu*g); achieved-decel monitor | None | Demand and retry cannot overcome adhesion |

The C++ achieved-deceleration supervisor consumes an optional independently timestamped
input, not BrakeStatus's simulated actuator output. The SiL source is the previous plant
acceleration (an ideal noiseless longitudinal accelerometer abstraction), not current/future
truth. Validity, finite magnitude [0,15], future time and >100 ms age are checked. After
>300 ms established braking while moving, decel below min(half previous demand,2 m/s²)
for >=200 ms latches a diagnostic/unavailable indication. Normal standstill is exempt.
This is gross-under-delivery detection, not proof of sufficient stopping or an established
vehicle FTTI. The diagnostic cannot guarantee time for driver rescue. Alerts latch until
disable; fail-silent software simulation is only one possible failure mode.

The backup receiver is in C++, not a Python override that forces plant braking. Every
backup request passes CRC, sequence and payload validation. Both valid commands update the
same demand state; primary wins. CAN arbitration, congestion, channel-specific electrical
faults and independent fail-operational power are not modeled. Modulo-16 counters and CRC
are not freshness authentication. A delayed sequential inactive command may remain valid
while active backup demand exists: priority arbitration needs an age/identity contract
before a real design could claim latency-tolerant command authority.

## Updated qualitative FMEA

| Element failure | Item effect | Detection | Remaining action |
|---|---|---|---|
| Radar stale, camera healthy | Degraded sensing | Per-source acquisition age | Measured FI01 results; independent hardware/common-cause study required |
| Camera missed object | Radar may retain target | Availability/quality and union fusion | Ghost-vs-miss tradeoff, calibrated confidence, temporal association |
| Common sensor bias/ghost | Late or unnecessary brake despite agreement | Often undetected | Independent reference and diverse sensing/scene validation |
| Primary bus loss | Backup may preserve demand | E2E + supervision | Common power/bus routing and both-channel loss |
| Brake process fail-silent | No achieved brake | Status timeout + achieved mismatch | Independent brake-control authority absent |
| Actuator failed / adhesion low | Demand accepted, vehicle does not slow enough | Achieved mismatch | Hardware alternative/grip-aware planning absent |
| IMU absent/invalid | Loss of achieved-brake assurance | Timestamp/validity/range checks | IMU faults/grade/noise and independence validation |

## Updated qualitative fault trees

T1 collision despite AEB = insufficient usable perception OR insufficient delivered braking
OR premature release OR insufficient physical distance/adhesion. With healthy camera,
radar freeze alone is no longer a necessary collision cause in the tested FI01; correlated
perception loss/incorrect agreement remain cut-set candidates. With healthy backup transport,
primary loss alone is mitigated in the tested FI02. Brake ECU failure, shared actuator failure,
both-channel loss, adhesion insufficiency and false target rejection remain candidate
single-point causes under this inattentive-driver model. No probabilities or independence
assumptions are assigned. T2 harmful unnecessary brake = accepted ghost/false target OR
accepted forged/stale demand OR overlong hold; disagreement and missing evidence do not
justify universal emergency braking. `models/v0.3.0/fault_containment.puml` illustrates boundaries.
